# Map: Executive AI Learning Page

Label: `wayfinder:map`

## Destination

Every content, design, and instructional-method decision for the AI-for-Executives learning page is resolved and written down — so the build is a single execution session with nothing left to guess.

## Notes

**Domain.** A ~3-hour 1:1 AI enablement session for a senior executive, delivered as a click-through HTML site (PowerPoint-like navigation plus a section menu), not an actual deck. German. Reusable across clients — this executive is instance one, not the only one.

**Audience.** Senior executive who has poked at ChatGPT. Wants the foundation, wants to use it in daily work, wants to spot use cases inside their company. Opportunity-seeking, not anxious. North star: *"I just have Claude installed. How can this thing help me now?"*

**Source briefs.** `context/ai-exec-workshop-skill-prompt.md` and `context/design-brief-claude-design.md`. Both are first drafts. Content, design, and instructional method are all open and all challengeable — find the reason behind a choice, then attack it. Nothing survives because it is already written down.

**Skills every session should consult.** `/grilling` and `/domain-modeling` for decision tickets; `/prototype` for anything answering "how should it look" or "how should it behave".

**The central metaphor — confirmed, and it governs everything.** *The assistant you always wished for.* A capable colleague you have just hired: extremely well read, tireless, available at eleven at night, no memory of yesterday unless you remind it, occasionally confidently wrong. The executive's job is to know how to instruct it, run it, and help it — not to understand it. Every limitation is an onboarding quirk, never a technical flaw. Every strength is a reason to hand something over. When a prompt works better, name why in delegation language.

**Standing constraints.**
- No EU AI Act, Article 4, regulatory, or compliance content. Ever. Do not reintroduce it in any form.
- No jargon that sounds like software. Never the words "prompt engineering" — say "a better brief". Delegation language throughout.
- Vendor-neutral. Teach the technology, use Claude for labs because that is what they have.
- Slides carry real content. The brief's "at most three lines per slide" is dead — it was a deck constraint and this is not a deck.

**Sequencing: content leads, design follows — with one deliberate exception.** Lesson-level design cannot be settled before the content it holds exists; a lab layout depends on knowing what a lab contains. But the *shell* — navigation model, the ladder rail, and above all how dense a content-carrying page can get before it stops feeling premium — runs early and on placeholder content, because what it teaches feeds straight back into how much content can be written. So: shell prototype now, lesson-level design pass after the sequence and lab set lock. The teaching model precedes both, since it decides what a "lesson" is.

**Plan, don't do.** Tickets produce decisions and rough prototypes to react to. They do not produce the shipped site. The pull to start building the real thing is the signal the map is finished.

**Priority, set 2026-07-27: session one first, session two is a first draft.** The user wants session one finalized and buildable soon. Session two's content (both the sequence table and any tickets that only affect session two) is real but provisional — good enough to hold the shape, not yet worth the same scrutiny. Sessions rarely resolves independently, so where a ticket blocks *both* (e.g. [The lab set](issues/04-lab-set.md) covers labs across both sessions), finish session one's half first and let session two's half trail. Do not let session-two polish gate a build.

## Not yet specified

- **The matrix bubble colour.** [The use-case backlog and matrix](issues/06-backlog-matrix-prototype.md) kept category colour on the matrix bubbles by default but flagged it as unsettled — no stronger alternative (no colour, colour by lens, colour by repeat flag) was proposed or tried during the reaction.
- **German register and tone.** Du or Sie, and how the warm/slightly playful tone survives translation. The brief's voice was written in English and does not carry over automatically. *Working assumption from [The sweet-spot pattern vocabulary](issues/02-sweet-spot-taxonomy.md): **Sie**, used throughout every name and example decided there. Not a decision — the tone half is untouched, and reversing to Du would mean rewriting that ticket's copy.*
- **How much automation content the session carries.** [The AI-versus-automation decision tree](issues/14-ai-vs-automation.md) fixes the tree's three branches, but the wider question — whether this stays an AI session that names automation's existence or starts advising on workflow tooling — is bigger than that ticket and may need its own scoping.
- **The reusable-brief lab.** Whether Lab 5 survives the reshape, and what concrete artifact the executive leaves holding.
- **How the page supports the follow-up program.** [The teaching model](issues/12-teaching-model.md) settled the *inter-session* week (JSON handoff, session two opens on the evidence). What the page does for the ongoing weekly catch-ups after both sessions is still open.
- **Full per-client customization of the showcase and all labs — the standing target, deferred past this build.** Two tiers, not to be conflated: **(1) ships now** — [The lab set](issues/04-lab-set.md) settled lab example prompts using a hand-edited `{{Rolle}}/{{Branche}}/{{Publikum}}/{{Firma}}` variable block, baked in at deploy time same as the matrix seed; the showcase (the pension-fund minutes) stays hardcoded to Doris's real documents for instance one. **(2) the target for client two and beyond, not yet scoped** — the user's stated intent is that the opening showcase *and* every lab are genuinely customized per client, which for the showcase means swapping in a new client's own real documents (an authoring task each time, not a variable swap), and for the labs may mean generating new questions/examples from client inputs rather than filling a fixed template. **Note the constraint tier 2 will run into:** the map's Out of scope already rules out any embedded LLM/API inside the page, so any generation-assisted version could only ever be an offline authoring-time tool, never a live in-page feature.
- **The take-home handout's delivery mechanism.** [How deep the theory goes](issues/03-theory-depth.md) fixed the content shape (quiz + exercises `.md`, downloadable at session one's close) but not how the download actually works against the site's read-only/no-storage rule — client-side generation, a build-time static file, or something else. Belongs to [Hosting and handover](issues/11-hosting-handover.md) once scoped precisely enough to ticket.
- **Where Skills lands in session two.** [How deep the theory goes](issues/03-theory-depth.md) moved Skills entirely out of session one; it now needs a real slot in session two, opening on the Project she built over the week rather than a saved brief. Likely sits inside session two's existing "Vom Gespräch zum Auftrag" block, but not yet written into that row or budgeted.
- **The German-language behaviour check.** [The capability arc](issues/16-capability-arc-research.md) found *no* first-party documentation of how memory, projects, connectors or agentic modes behave in German. The whole session is German. This is a task-shaped verification that must happen before delivery, and it is not yet a ticket because its scope depends on which features the final sequence actually touches.
